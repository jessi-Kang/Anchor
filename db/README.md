# db/

Postgres 스키마는 `migrations/*.sql` 의 순서대로만 바뀐다. ORM 자동 생성 없음.

## 실행

```bash
# .env.local 에 DATABASE_URL_ADMIN(또는 DATABASE_URL), ANCHOR_APP_PASSWORD 설정 후
pnpm db:migrate            # 미적용 파일을 순서대로 적용 (각 파일은 하나의 트랜잭션)
pnpm db:migrate:status     # 적용 상태만 출력
```

### 이 컨테이너에서 로컬 DB 를 세우는 법 (2026-09-21 에 실제로 세워 봄)

Postgres 16 이 깔려 있지만 **안 떠 있고 `anchor` DB 도 없다.** 세션마다 새로 세운다 —
`sudo -n` 이 통하므로 **기존 DB 를 건드릴 필요가 없다**(이름 바꾸기·지우기를 시도하면
권한 가드에 걸린다. 걸리면 우회하지 말고 새로 만든다):

```bash
sudo -u postgres /usr/lib/postgresql/16/bin/pg_ctl -D /var/lib/postgresql/16/main \
  -l /tmp/pg.log -o "-c config_file=/etc/postgresql/16/main/postgresql.conf" start
sudo -u postgres psql -c "CREATE DATABASE anchor" -c "CREATE ROLE anchor_app LOGIN PASSWORD '<로컬용>'"
sudo -u postgres psql -c "ALTER ROLE postgres PASSWORD '<로컬용>'"

export DATABASE_URL_ADMIN="postgres://postgres:<로컬용>@localhost:5432/anchor"
export ANCHOR_DATABASE_URL="postgres://anchor_app:<로컬용>@localhost:5432/anchor"
export ANCHOR_APP_PASSWORD='<16자 이상>'
pnpm db:migrate && pnpm db:seed
```

**걸리는 자리 다섯** — 다섯 다 오류 메시지가 원인을 안 말해 준다:

| 증상 | 까닭 |
| --- | --- |
| `SASL: client password must be a string` | 소켓이 아니라 TCP 로 붙어서 **`postgres` 역할에 비밀번호가 있어야** 한다 |
| `0001_init.sql: ANCHOR_APP_PASSWORD (16자 이상) 가 필요하다` | 말 그대로 **16자 이상**이어야 한다 |
| 시험 로그인이 `/` 로 튕김 | `ANCHOR_TEST_LOGIN=1` 만으로는 안 열린다. **`ANCHOR_TEST_USER_ID`** 가 있어야 하고(`src/lib/auth/test-login.ts`, 기본값 없음) 그 id 의 행이 `users` 에 있어야 한다 |
| `pnpm verify` 가 DB 시험 **5개**만 빨강 | 마이그레이션만 하고 **`pnpm db:seed` 를 안 돌렸다.** 시험이 씨앗 행을 본다 — 코드가 깨진 게 아니다 |
| `pnpm verify` 가 **`build` 에서** 죽는다: `Failed to collect page data for /api/auth/[...path]` → `환경 변수 NEON_AUTH_BASE_URL 가 설정되지 않았다` | DB 와 **무관하다.** `next build` 가 페이지 데이터를 모으면서 `src/lib/auth/server.ts` 를 평가하는데 그게 모듈 최상단에서 `env.NEON_AUTH_BASE_URL` 을 읽는다. **빌드는 인증 서버에 붙지 않으므로 자리표시 값이면 통과한다** — `NEON_AUTH_BASE_URL=http://localhost:9999/auth`, `NEON_AUTH_COOKIE_SECRET=<32자 이상 아무 값>`. 진짜 값을 찾아다니지 마라 |

그 계정으로 `/today` 가 열리려면 `settings` 가 **중첩된 꼴**이어야 한다 — 평평한
`{"languages":["ja"]}` 는 안 먹는다(`src/lib/db/settings.ts`):

```sql
UPDATE users SET settings = jsonb_build_object(
  'languages', jsonb_build_object('ja', jsonb_build_object('enabled_at', now()))
) WHERE id = '<시험 계정 id>';
```

**왜 여기 적나.** 이것들은 2026-09-21 에 여러 세션이 따로 막혔던 자리인데 **답이 쪽지에만
있었다.** 쪽지는 세션과 함께 사라지고, 다음 사람은 `db/README.md` 를 연다.

**다섯째 줄은 이 문서 제목과 안 맞아 보인다 — 일부러 여기 둔다.** `db/` 이야기가 아니라
`pnpm verify` 이야기라서다. 그런데 **막힌 사람은 `pnpm push` 가 빨간 걸 보고 이 문서를
연다**(`scripts/push.sh` 가 빨강일 때 이 파일을 가리킨다). 맞는 문서에 적어 두고 아무도 안
여는 것보다, 여는 문서에 적어 두는 쪽이 낫다. 잰 값: 이 컨테이너에는 `.env` 도 환경 변수도
없었고, 자리표시 두 개만 넣으니 `build` 가 통과했다(2026-09-21).

### 이력이 얕다 — 「그 커밋 없는데?」 는 십중팔구 이것

이 컨테이너의 클론은 기본이 **shallow** 다(세션 시작 때 481 커밋). 경계 너머 커밋은
`git log` 도 `git cat-file -e` 도 **「없다」**고 답한다. 잘리는 쪽이 오래된 쪽이라
「마지막으로 건드린 커밋」류는 안 틀리지만, **「X 는 이력에 없다」류는 못 믿는다.**

```bash
git rev-parse --is-shallow-repository   # true 면 아래를 먼저
git fetch --deepen=500 origin main
```

적용 기록은 `schema_migrations(name, applied_at, checksum)` 에 남는다. 이미 적용된 파일의 내용이 바뀌면 체크섬 불일치로 중단한다. 새 변경은 항상 새 파일로.

## 프로덕션에 올라간 마이그레이션

**아래는 계획이 아니라 돌린 뒤 `SELECT name, checksum FROM schema_migrations` 로 읽은 값이다.** 올리기 전에 적으면 그것은 계획이고, 부분 실패하면 이 문서가 조용히 틀린다.

| 마이그레이션 | 원장의 체크섬 | 원장의 적용 시각 (UTC) |
| --- | --- | --- |
| `0007_measure_columns.sql` | `dc498df7fb86…` | 2026-09-21 04:29:38 |
| `0008_recordings_client_id.sql` | `b505a4f0e9bc…` | 2026-09-21 04:29:48 |

`0001`~`0006` 은 2026-09-20 에 올라가 있다. 읽은 시점(2026-09-21 04:5x)에 원장은 **여덟 행**이고 여덟 개 다 `db/migrations/` 와 이름이 같다.

**`0007` 은 적용 전에 제자리에서 한 번 고쳐졌다**(`c6c21ae` → `5b7968d`, 합성 표식 열을 뺐다). 프로덕션에는 **고친 뒤 값**(`dc498df7fb86…`)이 올라갔다. 고치기 전 값은 `100f2d2c5a4d…` 다 — 어딘가의 원장이 그 값을 들고 있으면 그 DB 는 옛 파일을 적용한 것이고, `pnpm db:migrate` 가 거기서 멈춘다. **멈추면 멈춘 채로 알린다. 원장 행을 손으로 맞추지 않는다** (`docs/TEAM.md`).

**그 일이 실제로 났다** (2026-09-21, `d12d9fb`). 옛 값을 들고 있는 원장이 **개발 컨테이너에 한 대** 있고 거기서 `db:migrate` 가 0007 에서 멈춰 0008 까지 못 갔다. **그 대는 고치지 않고 표본으로 둔다** — 되돌리는 마이그레이션을 내지 않는다. 까닭은 이렇다: **처음부터 세운 DB 는 장부에 지금 파일의 체크섬을 그 자리에서 적으니 언제나 맞는다.** 그래서 `pnpm test:db` 의 `db-provenance` 가 초록인 것은 **어긋남이 없다는 뜻이 아니라 어긋날 수 있는 DB 가 아니라는 뜻**이고, 어긋남은 **옛 파일로 한 번 돌린 DB 에서만** 드러난다. 그 한 대가 그걸 볼 수 있는 유일한 자리다. 새로 세워 쓸 DB 는 따로 만든다.

**위 표는 살아 있는 읽기가 아니라 2026-09-21 04:5x 에 읽어 적은 기록이다.** 프로덕션이 그 뒤로 움직였는지는 이 문서가 모른다. **이 물음이 다시 열리는 조건은 하나다** — 프로덕션에서 `pnpm db:migrate` 가 0007 에서 멈추는 것. 그때는 위 규칙대로 멈춘 채로 알리고, 이 표를 다시 읽어서 고친다.

### 멈춘 DB 를 지나가게 하는 길 — 설계는 끝나 있고, 안 낸다

멈춘 DB 를 지나가게 하려면 **둘이 한 쌍**이다.

```
① scripts/migrate.ts 의 INTENTIONAL_EDITS 에 0007 짝 하나   100f2d2c5a4d… → dc498df7fb86…
② 새 마이그레이션: 옛 0007 이 만든 열 셋을 DROP COLUMN IF EXISTS
     encounters.meta · recordings.meta · cards.meta  (셋 다 읽는 코드가 없다 — 재 봤다)
```

옛 판을 돌린 DB 는 ①로 지나가고 ②가 남은 열을 걷어내며, 지금 판을 돌린 DB 는 체크섬이 이미 맞고 ②가 `IF EXISTS` 라 아무것도 안 한다. **둘이 같은 자리에 선다.**

**그런데 안 낸다.** 지금 옛 값을 들고 있는 건 **버려도 되는 작업용 DB 한 대**고, 그 대의 더 싼 길은 옆에 새 DB 를 세우는 것이다(이미 그렇게 했다). ①+②는 **레포에 영구 항목을 둘 남기는 거래**이고, 게다가 위에 적은 **표본 한 대를 지운다.**

**다시 열 조건:** 언젠가 **다시 못 세우는 DB**(프로덕션이거나 진짜 사용자 행이 든 DB)가 `100f2d2c5a4d…` 를 들고 있는 것이 확인되면, **그때 ①+②가 답이고 설계는 위에 이미 끝나 있다.**

**그리고 「0008 로 되돌리는 길」은 쓰지 마라.** `5b7968d` 커밋 본문이 *"이미 돌린 곳이 있으면 0008 로 되돌리는 쪽으로 낸다"* 고 적어 두었는데, **그건 그 줄을 쓸 때 참이었고 지금은 아니다** — 그 뒤로 **지금 판으로 이미 돌린 DB 가 생겨서**, 되돌리면 그쪽이 거꾸로 어긋난다. 위 ①+②가 그 자리를 대신한다.

**규칙 둘 (여기 말고 다른 검사에도 선다):**

- **검사에 예외를 선언하기 전에, 예외 없이 초록을 만드는 길이 있는지 먼저 본다.**
- **①(체크섬 예외)은 ②(스키마를 실제로 맞추는 것) 없이 혼자 가지 않는다.** ①만 넣으면 그 DB 는 **어긋난 채로 영영 초록**이 되고, 그건 고친 게 아니라 **검사를 끈 것**이다.

## 프로덕션에 올라간 공용 씨앗

### 씨앗 적재는 어느 축에서 검증됐나 (2026-09-21 12시대)

적재를 프로덕션에 돌리기 전에 네 축에서 태웠다. **무엇을 못 봤는지도 같이 적는다.**

| 무엇을 봤나 | 어느 축 | 결과 |
| --- | --- | --- |
| 찍어낸 SQL 이 `pnpm db:seed` 와 같은 상태를 만드나 | 리더: 빈 DB 둘 · 내용 해시 | 노드 `f74520d4…` 엣지 `fdf561a0…` **양쪽 같다** |
| 같은 물음, **해시 정의를 새로 짜서** | PM 축: 자기 로컬 DB 둘 | 노드 `01d6e51d…` 엣지 `01e55c16…` **양쪽 같다**. 덮는 칸이 다른데 결론이 같다 |
| 908KB 를 마이그레이션 올라간 DB 에 통째로 | PM 축 | 제약에 **한 줄도 안 걸렸다** |
| **이미 씨앗이 든 DB 에 한 번 더** (멱등) | PM 축 | 행 수·해시 **한 자리도 안 움직였다** |
| **낡은 값 위에 덮으면 어떻게 되나** | PM 축: 일부러 틀린 40행(`ko_word:"엉터리"`, `parts:[]`, `reading:'エセ'`)을 심고 덮음 | **정본으로 수렴. 엉터리 남은 것 0** |
| **낡은 엣지가 있으면 어떻게 되나** | PM 축: 낡은 엣지 하나(`sound 김` + `김 -ko_sound_of-> 金`)를 심고 통째로 재적용 | **안 지워진다.** 엣지 6,049(`ko_sound_of` 2,136) · `sound` 428 · 김→金 살아 있음 |

**마지막 줄이 프로덕션 모양이다** — 프로덕션은 빈 DB 가 아니라 40행이 있는 DB 다. 그리고 이것이 `jsonb ||` 위험(옛 값이 살아남는 것)이 **SQL 경로에서도 안 난다**는 뜻이다. 지금까지 그 보증은 `scripts/seed.ts` 쪽에만 있었다.

**낡은 엣지 줄이 읽는 법을 하나 늘린다.** 적재 SQL 은 노드는 갈아 끼우지만 **엣지는 지우지 않는다.** 그래서:

```
엣지 6,048        정상
엣지 6,048 + n    낡은 ko_sound_of 엣지 n 개다. **적재 실패가 아니다** — fb3ea01 이 지울 것이다
```

**이 줄이 없으면 6,059 를 보고 「적재가 깨졌다」로 읽는다.** 개발 데이터가 파일·DB 대조로 낸 그 수(낡은 11 + 새로 붙는 5)와 PM 축이 하나를 심어 본 것이 **메커니즘이 같다** — 계산 한 축, 심기 한 축.

그리고 이것이 **순서(적재 → `fb3ea01`)가 맞는 이유를 하나 더 준다.** 적재는 엣지를 안 건드리는 판에서 돌고, 엣지 규칙은 그다음에 혼자 들어간다. **한 번에 두 가지를 안 바꾼다.**

**아직 못 본 것 하나.** 심은 40행은 전부 `kind='kanji'` 였다 — **프로덕션 40 이 어떤 종류인지는 아무도 안 셌다.** 기록에 있는 것은 행 수뿐이고, **적재가 끝나면 사라지는 물음이라 안 산다.**

**주의 — 「프로덕션엔 지울 엣지가 애초에 없다」는 접힌 말이다.** 그 문장은 **「프로덕션 40 = `ja-seed.json` 의 40」**이라는 전제 위에 있었고, 그 전제는 센 적이 없어서 철회했다(위 문단). 그러니 **낡은 엣지가 없다고 기대하지 말고, 있으면 위 표로 읽는다.**

### 프로덕션 적재는 무엇이 돌리나 — **액션이 `pnpm db:seed` 를 돌린다**

**`.github/workflows/seed.yml` 은 2026-09-21 14:15 UTC 에 Jessi 가 직접 올렸다(`bba648e`).** 그 전까지는 레포에 없었다 — 커밋이 권한 분류기에 `[Production Deploy]` 로 막혀 파일만 Jessi 에게 갔었다. **그래서 여는 사람마다 다르게 알고 있었다** — 「SQL 을 MCP 로」와 「액션이 스크립트를」이 같은 날 같이 돌았다. 열 파일이 없으면 기억끼리 부딪친다. 그 파일이 무엇을 돌리는지를 **여기 박아 둔다:**

```
손으로만 돈다 (workflow_dispatch, 일정 없음)
  ① pnpm tsx scripts/seed-count.ts    적재 전 행 수
  ② pnpm db:seed                      적재 — 검증된 스크립트 경로
  ③ pnpm tsx scripts/seed-count.ts    적재 후 행 수
비밀값은 레포 시크릿 DATABASE_URL_ADMIN (nightly-backup 이 이미 쓰는 것)
```

**찍어낸 SQL(`scripts/seed-sql.ts`)은 예비 길이다.** 지금 고른 길이 아니고, 그 길로 가는 날은 출력이 `INSERT 0 N` 뿐이라 세 줄이 안 나온다.

**위 상자는 한때 파일이 아니라 옮겨 적은 것이었다.** 그래서 「파일이 올라오면 맨 먼저 맞대어 본다」를 여기 적어 뒀고, **파일이 올라온 날 두 자리에서 따로 맞대어 봤다(2026-09-21 14:1x~14:2x UTC). 한 칸도 안 달랐다.** 상자에 없고 파일에만 있던 것은 `permissions: contents: read` 와 `timeout-minutes: 15` 둘뿐이다.

**그러니 이 절은 이제 「적혀 있다」가 아니라 「열어 봤다」이고, 다시 셀 일이 아니다.** 옮겨 적은 것이 맞았다고 옮겨 적기가 안전해지는 건 아니다 — 맞대어 볼 수 있게 된 순간 맞대어 봤기 때문에 닫힌 것이다.

**그러니 읽는 규칙을 길에 매달지 않는다:**

| | |
| --- | --- |
| **출력 모양으로 판정하지 않는다** | 세 줄이 나오든 안 나오든, 그것만으로는 성공도 실패도 아니다 |
| **수는 DB 에 직접 묻는다** | 아래 칸별 질의. `seed-count.ts` 가 그걸 한다 |
| **6,048 + n 은 실패가 아니다** | 낡은 `ko_sound_of` n 개 (위 절) |

**이 규칙이면 두 길 어느 쪽이든 안 물린다.** PM 축 제안이고, 길이 바뀌어도 안 낡는다는 점에서 위 상자보다 세다 — 상자는 지금 고른 길을 적은 것이라 **길이 바뀌면 같이 고쳐야 한다.**

### 적재가 끝난 뒤 무엇을 보고 통과라 하나 — **길이 둘이라 보는 것도 둘이다**

**길에 따라 화면에 나오는 것이 다르다.** 이것을 안 적어 두면 **아무것도 안 나온 것**을 「안 돌았나」로 읽는다.

| 길 | 화면에 나오는 것 |
| --- | --- |
| `pnpm db:seed` (스크립트가 직접 연결. 깃헙 액션도 이쪽이다) | `en-seed: 40 노드` · `부품: 505 노드` · `한자: 2136 노드, 한국 한자음: 427 노드, 엣지: 6048` |
| 찍어낸 SQL 을 Neon MCP 로 (`scripts/seed-sql.ts`) | **그 세 줄이 안 나온다.** `INSERT 0 N` 만 흐른다 |

> **지금 고른 길은 첫째 줄이다** — 아래 「프로덕션 적재는 무엇이 돌리나」 절에 액션이 무엇을 돌리는지 박혀 있다. 그러니 **세 줄은 나오고, 앞뒤로 행 수까지 찍힌다.**
>
> **그런데 출력 모양으로 판정하지는 않는다.** 이 자리에 한때 「프로덕션은 SQL+MCP 쪽」이라고 적혀 있었다 — `seed-sql.ts` 의 **주석**을 읽고 적은 것이고, 정하는 파일(`seed.yml`)은 그때 레포에 없었다. **같은 날 두 사람이 같은 이름(「프로덕션 적재」)을 두고 반대로 알고 있었고, 둘 다 참인 문장을 들고 있었다.** 길이 한 번 갈리면 「세 줄이 없다」가 정상도 되고 신호도 된다.
>
> **그래서 규칙은 길을 안 타는 쪽에 둔다. 아래 질의가 어느 길에서도 선다** — DB 에게 직접 묻는 것은 길과 무관하기 때문이다. 지금 길에서는 액션이 앞뒤로 `scripts/seed-count.ts` 를 찍으니 **그 수를 그냥 읽으면 되고**, 수가 없거나 길이 바뀌면 이 질의를 돌린다.

**예비 길(SQL + MCP)로 가는 날에는 위 세 줄이 아예 없다.** 그 수는 씨앗 스크립트가 *입력을 센* 값이지 DB 가 답한 값이 아니라서, SQL 경로에는 셀 사람이 없다. 그래서 **적재 뒤에 DB 에게 직접 묻는다** — `scripts/seed-count.ts` 는 연결 문자열을 여는 스크립트라 MCP 길에서는 못 쓰고, 같은 것을 한 줄로 묻는 질의를 둔다:

```sql
SELECT '한자' AS 무엇, count(*) FROM nodes WHERE user_id IS NULL AND lang='ja' AND kind='kanji'
UNION ALL SELECT '부품',        count(*) FROM nodes WHERE user_id IS NULL AND lang='ja' AND kind='radical'
UNION ALL SELECT '한국 한자음', count(*) FROM nodes WHERE user_id IS NULL AND lang='ko' AND kind='sound'
UNION ALL SELECT '영어',        count(*) FROM nodes WHERE user_id IS NULL AND lang='en'
UNION ALL SELECT 'part_of',     count(*) FROM edges WHERE user_id IS NULL AND rel='part_of'
UNION ALL SELECT 'ko_sound_of', count(*) FROM edges WHERE user_id IS NULL AND rel='ko_sound_of'
UNION ALL SELECT '엣지 합계',   count(*) FROM edges WHERE user_id IS NULL;
```

**서야 할 수** (`db/seed/kanji.json` 이 `d79ba91`, `parts-ko.json` 이 `ce82324` 일 때 파일에서 유도한 값. 2026-09-21 13:2x UTC):

```
한자 2136 · 부품 505 · 한국 한자음 427 · 영어 40
part_of 3913 + ko_sound_of 2135 = 엣지 합계 6048
```

**어긋나면 어디가 어긋났는지가 그 자리에서 보인다.** 합계만 적어 두면 「6,048 이 아니다」까지만 알고 어느 칸인지는 다시 세야 한다.

> **빚 하나.** `seed.yml` 머리 주석에도 같은 수(2,136 · 505 · 427 · 40 · 6,048)가 적혀 있다. 데이터가 움직이면 거기도 낡는데 **기댄 커밋이 옆에 없다.** 지금은 안 고친다 — 검증한 판과 도는 판이 달라지면 안 되기 때문이다(그 파일은 `bba648e` 그대로 두 자리에서 맞대어 봤다). **그 파일을 다음에 만질 때 수를 빼고 이 표를 가리키게 한다.**

**그리고 어긋난 수가 다 같은 뜻이 아니다. 위로 어긋난 것은 대개 실패가 아니다:**

| 나온 수 | 뜻 |
| --- | --- |
| 엣지 **6048** | 정상. 낡은 것이 없다 |
| 엣지 **6048 + n** | **낡은 `ko_sound_of` 엣지가 n 개 있었다.** 적재가 깨진 게 아니다 — 적재 SQL 은 없던 줄을 넣을 뿐 낡은 줄을 안 지운다. 지우는 것은 `fb3ea01` 이고, **순서가 그래서 그 순서다** |
| 소리 **427 + m** | 그 낡은 엣지가 아직 붙들고 있는 소리 노드 m 개. `fb3ea01` 이 엣지를 지우면 같이 빠진다 |
| 그 밖 | 다른 것이다. 위 질의로 칸별로 다시 센다 |

**「실행이 생겼다」와 「적재가 됐다」는 다른 물음이다.** 수를 읽기 전에 이것부터 가른다:

| 실행 | 적재 | 어떻게 아나 |
| --- | --- | --- |
| `conclusion: success` + ③ 「적재 후 — 몇 행이 섰나」가 로그에 찍혔다 | **됐다** | 그 ③ 의 수가 읽을 값이다 |
| 실패 · 취소 · 시크릿 없음 | **안 됐다** | ② 에 닿지도 못했으면 DB 는 한 줄도 안 바뀐다 |

**실제로 났다.** 2026-09-21 14:19:08 UTC 실행 #1 은 `conclusion: failure` 로 18초 만에 끝났다 — ① 에서 `DATABASE_URL_ADMIN` 이 비어 있어 멈췄고 ②③ 은 건너뛰었다. **실행은 하나 생겼고 적재는 없었다.** 「실행이 하나라도 생기면 적재가 된 것」으로 읽으면 그 자리에서 틀린다.

> **레포 시크릿 `DATABASE_URL_ADMIN` 은 아직 없다.** `seed.yml` 머리 주석과 그 커밋이 「이미 `nightly-backup` 이 쓰는 시크릿」이라고 적었는데, **파일이 그 이름을 참조하는 것과 값이 들어 있는 것은 다른 말이다.** 2026-09-20 20:48 UTC 의 `nightly-backup` 실행 로그에서 그 칸이 이미 비어 있었다(`BACKUP_S3_*` 다섯도 같이). 그러니 다음 걸음은 **버튼을 한 번 더 누르는 것이 아니라 시크릿을 먼저 넣는 것**이다.
>
> **가르는 법은 로그 한 줄이다** — Actions 로그의 `env:` 묶음에서 **값이 있으면 `***`, 없으면 빈칸**이다. 시크릿은 밖에서 못 읽지만 **있는지 없는지는 이렇게 읽을 수 있다.** 다음에 「그 시크릿 있나」를 물을 일이 생기면 기억이나 파일 참조 말고 이 줄을 본다. (두 자리가 따로 봤다 — 어제 `nightly-backup`, 오늘 `seed` 실행 #1. 다른 실행 · 다른 날 · 같은 빈칸.)
>
> (그 `nightly-backup` 실패 자체는 이상이 아니다 — 그 워크플로는 **선택**이고 헤더가 「없으면 실행이 실패하고 무시해도 된다」고 적어 뒀다. 매일 JSON 백업 층은 그쪽이 아니라 `/api/cron/backup`(Vercel cron → Blob)이다: `docs/BACKUP.md` 1장.)

**그리고 이 줄이 없으면 `6,059` 를 보고 「적재가 깨졌다」로 읽는다.** PM 축이 2026-09-21 13:2x UTC 에 한 개짜리로 줄여 태워 봤다 — 정본 상태 DB 에 `김 -ko_sound_of-> 金` 하나를 심고 SQL 을 통째로 다시 덮으니 `소리 428 · 엣지 6049` 가 그대로 남았다. **재적용이 낡은 줄을 안 지운다는 것이 한 줄 크기에서도 같다.**

> **「영어 40」은 씨앗 40자와 다른 40 이다.** 이쪽은 영어 어근 22 + 덩어리 18 이고 `ja-seed.json` 의 40자와 아무 상관이 없다. 같은 수가 두 뜻으로 나란히 서는 유일한 자리라, 이 줄만 보고 「일본어 씨앗이 들어갔네」로 읽지 않는다.

**묵은 DB 의 지문도 적어 둔다.** 위 수는 *빈 DB 에 지금 파일로* 넣었을 때의 값이다. **옛 데이터로 한 번 심고 그대로 둔 DB** 는 다르게 답한다. 이 레포의 로컬 DB 를 2026-09-21 13:2x UTC 에 세어 보니:

```
한국 한자음 429 (427 아님) · ko_sound_of 2130 (2135 아님) · 합계 6043
```

**어긋난 자리를 파일과 맞대어 셌다. 셋 다 이름까지 나온다:**

| 무엇 | 수 | 누구 |
| --- | --- | --- |
| DB 엣지가 파일과 **다른 소리**를 가리킨다 | **11** | 金→김 不→부 予→여 参→삼 率→솔 医→예 芸→운 則→즉 欠→흠 茶→다 索→삭 |
| 그래서 **DB 에만 있는 소리 노드** | **2** | 김 · 흠 |
| 파일엔 `ko` 가 있는데 **엣지가 없다** | **5** | 収 塡 頰 𠮟 剝 |

**셋이 한 줄로 이어진다.** 씨앗을 다시 돌리면 없던 5 개가 생겨 `2130 + 5 = 2135`, 그런데 **낡은 11 개는 아무도 안 지운다**(upsert 는 없던 줄을 안 건드린다) → `3,913 + 2,135 + 11 = 6,059`. `fb3ea01` 이 그 11 을 지우고, 그러면 김·흠 이 아무도 안 가리키는 소리가 되어 같이 빠진다 → **소리 427 · 엣지 6,048**. 이 표의 수가 곧 그 커밋이 하는 일이다.

**프로덕션은 이 모양이 아니다.** 거기는 40행뿐이라 낡은 엣지가 애초에 없고, 그래서 **밀기 전에 적재하든 뒤에 하든 6,048 이 나온다.** 이 지문은 「그 DB 가 언제 심은 DB 인가」를 가를 때 쓰는 것이지, 프로덕션에서 기대할 값이 아니다.

**주의 — 프로덕션에는 씨앗이 거의 안 들어가 있다.** 2026-09-21 04:5x 에 읽으니 공용 한자 노드(`user_id IS NULL AND lang='ja' AND kind='kanji'`)가 **40행**이다. `db/seed/kanji.json` 은 2,136자다. `parts-sync` 는 **이미 있는 행만 고치는** 파일이라 지금 돌리면 40행만 손대고 나머지 2,096자는 애초에 없다. **부품을 맞추기 전에 씨앗 적재가 먼저다.**


| 무엇 | 커밋 | 언제 |
| --- | --- | --- |
| `db/seed/kanji.json` 의 `meta.parts` | **모름** | — |

**그리고 그 파일은 「없는 글자」를 세어서 말한다.** 안 그러면 40행 DB 에서 3번이 `아직 다른 노드 0` 을 내고, 그 0 은 파일이 스스로 정한 성공 조건이라 **「다 맞췄다」로 읽힌다** — 2,096자가 없는데도. 실제로 옛 판을 40행 탐침에 돌려 확인했다. 지금은 세 질의가 다 이렇게 낸다:

```
바뀔 노드 0 · 노드가 없는 글자 2096 · 파일에 적힌 글자 2136
```

**이 파일은 있는 행만 고친다.** 「노드가 없는 글자」가 0 이 아니면 씨앗 적재가 먼저다.

**이 칸이 비어 있으면 부품을 고칠 때마다 2,136자를 전부 찍어야 한다.** 무엇이 올라가 있는지 모르면 무엇이 달라졌는지도 모르기 때문이다. `pnpm seed:parts-sql --all` 은 그래서 안전하지만 파일이 길다.

적용한 사람이 여기 커밋을 적는다. 그 뒤부터는 `pnpm seed:parts-sql --since <그 커밋>` 으로 바뀐 것만 찍는다.

```bash
pnpm seed:parts-sql --all --out db/manual/parts-sync-<날짜>.sql   # 접속하지 않는다. SQL 만 찍는다
# 받은 사람이 파일을 읽고 돌린다. 1번 질의가 실제로 바뀔 줄 수를 먼저 알려 준다.
```

찍어낸 UPDATE 는 `meta->'parts'` 가 **실제로 다른 줄만** 건드린다. 두 번 돌리면 두 번째는 0 줄이다.

`manual/` 은 마이그레이션이 아니다. `pnpm db:migrate` 가 안 본다. 한 번 손으로 돌리고 나면 위 표에 커밋을 적고 파일은 기록으로 남긴다.

## 두 개의 연결

| 변수 | 역할 | 쓰는 곳 |
| --- | --- | --- |
| `DATABASE_URL_ADMIN` (없으면 `DATABASE_URL`) | 테이블 소유자 (Neon 기본 역할). Vercel Neon 통합은 이걸 `DATABASE_URL` 로 주입한다 | 마이그레이션, 공용 참조 데이터 적재, 백업 |
| `ANCHOR_DATABASE_URL` | `anchor_app` (BYPASSRLS 없음, 0001 이 SQL로 생성) | 앱 런타임 전부 |

Neon 콘솔·API로 만든 역할은 `neon_superuser` 멤버라 RLS를 우회한다. 앱 역할을 콘솔에서 만들면 RLS가 무력화된다. 반드시 마이그레이션이 만든 `anchor_app` 을 쓴다.

## DB 를 쓰는 테스트

```bash
pnpm test:db     # DATABASE_URL_ADMIN 과 ANCHOR_DATABASE_URL 둘 다 필요하다
```

**수보다 먼저 출처 한 줄이 나온다.**

```
DB: anchor_local@127.0.0.1:5432 (anchor_owner)
마이그레이션: 0001–0008 적용 (8/8) · 레포와 8/8 일치
※ 아래 초록·빨강은 이 상태 위의 값이다.
```

**조건 없는 초록이 거짓말을 하기 때문이다.** 같은 명령이 한 컨테이너에서는 전부 초록이고 다른 컨테이너에서는 셋이 빨강이던 날이 있었다 — 뒤쪽에 `0008` 이 없어서였고, 그건 그 셋이 제 일을 한 것이다. 그런데 앞쪽 초록만 인용되면 **막힌 마이그레이션이 풀렸다는 뜻으로 읽힌다.** 숫자에는 어느 값 위에서 난 것인지를 붙인다.

**어긋나면 같은 줄이 그것도 말한다** — 맞을 때만 말하는 줄은 맞다는 것을 증명하지 못한다:

```
마이그레이션: 0001–0007 적용 (7/8)
  안 올라간 것: 0008_recordings_client_id.sql
  어긋난 것: 0007_measure_columns.sql (원장 100f2d2c5a4d… / 레포 dc498df7fb86…)
```

**어긋나도 멈추지 않는다.** 여기서 막으면 어긋난 쪽은 무엇이 지나가고 무엇이 떨어지는지조차 못 본다. 이 줄의 일은 막는 것이 아니라 말하는 것이다. 읽기만 하고 아무것도 안 고친다.

`scripts/test/*.test.ts` 는 `node:test` 로 돈다(의존성 없음). **앱 역할로 붙어 진짜 코드 경로를 타므로 RLS 까지 같이 시험한다** — 질의를 테스트에 베껴 쓰면 코드가 아니라 사본을 시험하게 된다.

쓰는 계정은 `fixture-` 로 시작하는 것뿐이고 끝나면 지운다. **프로덕션 연결로 돌리지 않는다.** 로컬이나 일회용 DB 를 쓴다.

### 갑자기 마흔일곱이 빨개졌을 때 — 「그거겠지」 대신 한 줄

로컬 Postgres 가 하루에 **열두 번** 죽었다. 한 번 죽을 때마다 DB 를 쓰는 테스트가 전부
`connect ECONNREFUSED 127.0.0.1:5432` 로 빨개진다. **낫지 않는 거짓 경보가 열두 번 울리면
열세 번째를 안 보게 된다** — 실제로 한 번은 "또 그거겠지" 하고 초록을 확인하기 전에 푸시했다.
사람 탓이 아니라 신호 탓이라, 짐작 대신 **가르는 한 줄**을 둔다:

```bash
uptime      # 기계가 방금 켜졌나
```

**기계(컨테이너)의 `up` 이 몇 분이면 Postgres 가 죽은 게 아니라 컨테이너가 회수된 것이다.**
`pg_ctlcluster 16 main start` 로 살리고 다시 돌리면 그대로 초록이다. 실제로 열두 번째 때
`up 9 min` 이었고, Postgres 로그의 마지막 줄은 **정상 체크포인트**였다(죽은 흔적이 아니다).

**기계가 몇 시간째 떠 있는데 Postgres 만 죽었으면 그건 진짜다.** 그때는 로그를 읽는다.

**살린 뒤에 한 번 더 볼 것 — 이 대의 DB 이름이 문서의 이름과 다를 수 있다.** 컨테이너가 회수되면
디스크째 사라지므로 DB 는 매번 새로 만들어지는데, `0001` 이 `current_database()` 를 쓰게 고쳐진
뒤로(`88ab8f0`) **이름에 제약이 없다.** 그래서 대마다 다른 이름이 섰다 — `anchor`(위 세우는 법),
`neondb`(`docs/QA.md` 의 길), `anchor_verify`(검증용으로 따로 세운 것). 셋 다 정상이다.

**그러니 이름은 문서에서 읽지 말고 제 환경에서 읽는다.** 문서의 이름을 그대로 치면 없는 DB 에
붙거나 엉뚱한 대의 데이터를 본다:

```bash
psql "$ANCHOR_DATABASE_URL" -c 'select current_database()'
```

**이 줄은 적은 날 값을 돌려줬다.** 같은 날 오후에 검증이 `38 pass / 48 fail` 로 떨어졌는데, 「또 그거겠지」로 넘기지 않고 `uptime` 을 먼저 봤다 — `up 1 min`. 빨강 마흔여덟이 내 변경과 무관하다는 것을 **짐작이 아니라 한 줄로** 알았고, 살리고 다시 돌리니 80/80 이었다. 30분 뒤에 한 번 더 났고 또 갈렸다. **이 문서의 규칙 중 회수된 적 있는 줄과 아직 아닌 줄은 무게가 다르다** — 이건 앞쪽이다.

### 그리고 판정을 파이프에 흘리지 않는다

```bash
pnpm test:db | grep "# pass" && git push     # ← 틀렸다
```

**`grep` 이 성공하면 `&&` 가 이어진다.** 빨간 줄 여덟이 떠 있어도 `# pass` 라는 **글자**를 찾은
것만으로 푸시가 나간다 — 실제로 그렇게 한 번 나갔다. 파이프는 **시험의 종료 코드를 버린다.**

**수를 눈으로 보는 것과 초록을 확인하는 것은 다른 일이다.** 수는 사람이 읽고, **통과 여부는
종료 코드가 말한다.**

### 밀기 — 손으로 잇지 않는다

```bash
pnpm push            # 가지에만
pnpm push --main     # 가지에 밀고 같은 커밋을 main 에도
```

**안에서 ① 합치고 → ② `pnpm verify` 로 재고 → ③ 조상인지 묻고 → ④ 민다.** 앞이 빨가면 ④에 안 닿는다. ①에서 충돌이 나면 거기서 멈춘다 — **풀고 이 명령을 다시 돌린다.** 풀어 놓고 나중에 미는 것이 곧 「미리 합쳐 둔 것」이라, 그 사이에 `main` 이 또 늙는다.

**왜 목록이 아니라 명령인가.** 전에는 이 자리에 따라 칠 bash 네 줄이 있었고, **이을 때마다 틀릴 자리가
생겼다.** 2026-09-21 하루에 셋이 났다 — `|` 가 판정을 삼켜 빨간 채 밀렸고, 합치기 뒤에 안 쟀고, `;` 로
이어서 푸시가 판정에 안 걸렸다. **셋 다 규칙은 이미 이 문서에 있었다.** 한 번은 사고고 셋이면
**규칙이 지켜지기 어려운 모양**이라는 값이라, 사람이 잇는 자리를 없앴다. 병합 커밋 제목이 「merge」
한 단어가 되던 것도 같이 사라진다 — 명령이 제목을 짓는다.

**②가 칸이 아니라 조건인 것**도 명령 안에서 지켜진다 — 「나무가 마지막으로 바뀐 뒤」. 커밋이나 두 번째
합치기가 끼면 나무가 또 바뀌고 앞에서 잰 것은 그 순간 검증이 아니게 되는데, **커밋은 이미 잰 작업
트리를 담는 것이라 안 세고 합치기는 남의 내용을 들이므로 언제나 센다.**

**①과 ②의 순서가 전에는 거꾸로였다.** 검증을 먼저 하고 합쳐서 밀면 **미는 것은 합친 결과인데 잰
것은 내 나무**가 된다 — 남의 커밋이 얹힌 채로 한 번도 안 재고 나가는 것이다. 실제로 그 차례대로
하다가, `main` 이 움직인 날 **합친 트리를 확인 안 한 채 프로덕션에 밀 뻔했다.** 합치기 전에도 재도
된다(내 것이 성한지 먼저 아는 값이 있다). **다만 미는 것을 묶는 판정은 ②다.**

**②와 ③이 하루에 한 번씩 샜다.** ②는 파이프가 판정을 버려서, ③은 **`fetch` 를 관계 확인으로 여겨서**다
— `fetch` 는 저쪽의 최신을 주지 **이쪽과의 관계**를 안 준다. 「최신을 받았다」와 「내가 그 위에 서
있다」는 다른 물음이고, 앞엣것으로 뒤엣것을 대신한 날 가지가 17커밋 뒤처진 채 fast-forward 라고 적혔다.

**셋 다 「했다고 여겼는데 안 물은」 자리**라 조심해서는 안 막힌다. 그래서 차례를 하나로 묶어 둔다.
여럿이 미는 동안엔 합친 순간부터 다시 늙으므로, ①은 밀 때 그 자리에서 한다 — 미리 합쳐 둔 것은
**「충돌을 미리 봄」**이지 밀 수 있게 된 것이 아니다.

붙들어 두는 것 넷. **내보내기 목록이 스키마에서 새지 않는가**, **계정 삭제가 모든 표에 닿는가** (아래), 그리고 **재전송 멱등 키**(0008)가 스키마에 서 있는가 — 이게 빠지면 다시 보낸 녹음이 새 회차로 앉아 5회차 자리에 4회차 소리가 앉는다. 그리고 **`encounters` 가 덧붙이는가**. 뒤쪽은 한 번 덮어쓰기로 돌아간 적이 있고, 그때 코드에는 반대로 적힌 주석이 또렷하게 달려 있었다. **틀려도 화면은 똑같이 돌고 인식률만 위로 부푼 채 D+14 까지 간다** — 그런 문장은 주석이 아니라 테스트로 적는다.

### 내보내기와 삭제 — 같은 질문의 양쪽

둘 다 "전부" 를 약속하는데 틀려도 티가 안 난다. 조용히 틀렸을 때 남는 말이 정반대다.

| | 조용히 틀리면 |
| --- | --- |
| 내보내기 | 사용자가 **다 가졌다고 믿는데** 안 가졌다 |
| 삭제 | 사용자가 **다 지웠다고 믿는데** 안 지워졌다 |

내보내기는 손으로 적은 표 목록을 돈다(`src/lib/db/export-tables.ts`). 삭제는 목록이 없다 — `users` 행 하나를 지우고 FK 가 CASCADE 로 흘리게 둔다. 목록이 없으니 목록 표류도 없어서 **삭제 쪽 설계가 낫다.** 대신 가정이 하나 생긴다: 사용자 행을 가진 표가 전부 `users` 까지 이어져 있다는 것.

두 규칙을 `pnpm test:db` 가 스키마에서 읽어 견준다. **차이가 있으면 선언된 차이여야 한다.**

- `src/lib/db/export-tables.ts` — 내보내는 표와 그 예외
- `src/lib/db/delete-paths.ts` — 삭제가 안 닿아도 되는 표와 그 이유

**FK 가 있다는 것과 지워진다는 것은 다르다.** 삭제 쪽 검사는 FK 의 존재가 아니라 **규칙**을 본다. `users` 로 가는 FK 의 규칙이 `SET NULL` 이면 행은 살아남는데, `nodes` · `edges` 는 `user_id` 가 NULL 을 허용하고 이 스키마에서 **NULL 은 "공용 참조 데이터"** 를 뜻한다(`0001_init.sql:92`). 지운 계정의 개인 노드가 주인만 잃고 남아 모든 계정이 읽게 된다 — 남는 것보다 나쁜 새는 것이고, "FK 가 있나" 만 보는 검사는 이걸 통과시킨다. 규칙만 `SET NULL` 로 바꿔 로컬에서 확인했다.

그리고 **권한 쪽은 내보내기보다 삭제가 나쁘다.** 내보내기는 `SELECT` 를 잃으면 질의가 터져 티가 난다. 삭제는 RLS 정책이 `DELETE` 를 안 덮으면 **`DELETE 0` 에 오류가 없다.** 라우트는 그대로 `{ ok: true }` 를 돌려주고 뒤이어 로그인까지 지워져 **다시 들어와 지울 길도 없다.** 그래서 스키마 검사와 별개로 라우트가 **지워진 행 수를 본다.**

## 회차는 왜 저장된 값인가 — 그리고 고칠 때 무엇이 답이 아닌가

`recordings.attempt` 는 서버가 INSERT 직전 `count(*)+1` 로 세어 **저장하는 파생값**이다. 제약이 없어서 같은 대상에 두 요청이 동시에 들어오면 **둘 다 같은 수를 받을 수 있다.** 그러면 `pnpm measure` 의 1회차·5회차가 둘 중 아무거나 집고, 표에는 멀쩡한 거리가 뜨는데 어느 회차를 잰 값인지는 모른다.

**아직 한 번도 안 일어났다.** 사용자가 한 명이고, 같은 덩어리에 동시 녹음이 나려면 두 탭이나 이중 제출이 있어야 한다. 그래서 지금은 고치지 않고 `pnpm measure` 가 그 대상 수를 머리말에 낸다. 그 대상을 표에서 빼지는 않는다 — 거리가 멀쩡해 보이는 것이 이 사고의 모양이라, 숨기면 더 나빠진다.

### `UNIQUE (대상, 회차)` 는 답이 아니다

걸면 동시 요청 둘 중 **둘째 쓰기가 실패한다.** 그 둘째는 사용자가 실제로 낸 녹음이다. **지금은 "거리를 못 믿는 행 하나" 인데, 유니크를 걸면 "사라진 녹음 하나" 가 된다** — `CLAUDE.md` 의 "추측 한 번, 녹음 한 번도 유실 없음" 을 깨는 쪽으로 바뀐다. 재시도를 붙이면 되긴 하지만, 그러면 유니크는 **재시도를 트리거하는 장치**지 답이 아니다.

### 답은 `attempt` 를 저장하지 않는 것

사실은 언제 말했는가이고 회차는 거기서 나오는 **판정**이다. 읽을 때 `row_number() OVER (PARTITION BY 대상 ORDER BY 말한 시각)` 로 매기면 세는 카운터가 없으니 **경합 자체가 없다.** `pnpm measure` 의 재만남 쪽이 이미 그 모양이다.

**다만 한 칸이 먼저 필요하다 — outbox 때문이다.** 저장 시각으로 매기면 **재전송이 역사를 다시 매긴다.** 오프라인에서 T1 에 말한 녹음이 T3 에 저장되면 저장 순서로는 그게 마지막 회차가 되는데, **말한 순서와 저장된 순서가 다른 것이 outbox 의 존재 이유다.** `0008` 은 `client_id` 만 달고 말한 시각이 없다.

> 파생으로 바꾸는 날, `client_id` 를 찍는 **그 자리에서** 「말한 시각」도 같이 찍는다. 순서는 저장 시각이 아니라 말한 시각으로 매긴다.

`client_id` 를 브라우저가 녹음을 만든 자리에서 붙이기로 한 것과 같은 이유다 — 서버가 만들면 재전송마다 달라지듯, 서버 시각으로 매기면 재전송마다 회차가 달라진다.

**급할 때 유니크로 손이 가지 않게 여기 적어 둔다.** 지금까지 쌓인 행은 `attempt` 가 저장돼 있어 그대로 읽히므로, 바꾸는 날 옛 행을 못 쓰게 되지는 않는다.

## RLS 동작 방식

```
withUser(userId, tx => ...)
  BEGIN
  SELECT set_config('app.user_id', $userId, true)   -- 트랜잭션 로컬
  ...쿼리...                                          -- 정책: user_id = app.current_user_id()
  COMMIT
```

- 설정이 없으면 `app.current_user_id()` 가 NULL → 모든 정책이 false → 아무 행도 안 보인다.
- 모든 사용자 테이블은 `FORCE ROW LEVEL SECURITY` 라 소유자 연결에서도 정책이 적용된다. admin 연결로 사용자 데이터를 보려면 `SET app.user_id` 를 해야 한다. 이건 의도된 마찰이다.
- `nodes`, `edges` 는 `user_id IS NULL` 행이 공용 참조 데이터(KANJIDIC2, IDS, 한자음, 어원)다. 읽기는 모두, 쓰기는 admin 스크립트만.
