# db/

Postgres 스키마는 `migrations/*.sql` 의 순서대로만 바뀐다. ORM 자동 생성 없음.

## 실행

```bash
# .env.local 에 DATABASE_URL_ADMIN(또는 DATABASE_URL), ANCHOR_APP_PASSWORD 설정 후
pnpm db:migrate            # 미적용 파일을 순서대로 적용 (각 파일은 하나의 트랜잭션)
pnpm db:migrate:status     # 적용 상태만 출력
```

적용 기록은 `schema_migrations(name, applied_at, checksum)` 에 남는다. 이미 적용된 파일의 내용이 바뀌면 체크섬 불일치로 중단한다. 새 변경은 항상 새 파일로.

## 프로덕션에 올라간 마이그레이션

**아래는 계획이 아니라 돌린 뒤 `SELECT name, checksum FROM schema_migrations` 로 읽은 값이다.** 올리기 전에 적으면 그것은 계획이고, 부분 실패하면 이 문서가 조용히 틀린다.

| 마이그레이션 | 원장의 체크섬 | 원장의 적용 시각 (UTC) |
| --- | --- | --- |
| `0007_measure_columns.sql` | `dc498df7fb86…` | 2026-09-21 04:29:38 |
| `0008_recordings_client_id.sql` | `b505a4f0e9bc…` | 2026-09-21 04:29:48 |

`0001`~`0006` 은 2026-09-20 에 올라가 있다. 읽은 시점(2026-09-21 04:5x)에 원장은 **여덟 행**이고 여덟 개 다 `db/migrations/` 와 이름이 같다.

**`0007` 은 적용 전에 제자리에서 한 번 고쳐졌다**(`c6c21ae` → `5b7968d`, 합성 표식 열을 뺐다). 프로덕션에는 **고친 뒤 값**(`dc498df7fb86…`)이 올라갔다. 고치기 전 값은 `100f2d2c5a4d…` 다 — 어딘가의 원장이 그 값을 들고 있으면 그 DB 는 옛 파일을 적용한 것이고, `pnpm db:migrate` 가 거기서 멈춘다. **멈추면 멈춘 채로 알린다. 원장 행을 손으로 맞추지 않는다** (`docs/TEAM.md`).

## 프로덕션에 올라간 공용 씨앗

**주의 — 프로덕션에는 씨앗이 거의 안 들어가 있다.** 2026-09-21 04:5x 에 읽으니 공용 한자 노드(`user_id IS NULL AND lang='ja' AND kind='kanji'`)가 **40행**이다. `db/seed/kanji.json` 은 2,136자다. `parts-sync` 는 **이미 있는 행만 고치는** 파일이라 지금 돌리면 40행만 손대고 나머지 2,096자는 애초에 없다. **부품을 맞추기 전에 씨앗 적재가 먼저다.**


| 무엇 | 커밋 | 언제 |
| --- | --- | --- |
| `db/seed/kanji.json` 의 `meta.parts` | **모름** | — |

**그리고 그 파일은 「없는 글자」를 세어서 말한다.** 안 그러면 40행 DB 에서 3번이 `아직 다른 노드 0` 을 내고, 그 0 은 파일이 스스로 정한 성공 조건이라 **「다 맞췄다」로 읽힌다** — 2,096자가 없는데도. 실제로 옛 판을 40행 탐침에 돌려 확인했다. 지금은 세 질의가 다 이렇게 낸다:

```
바뀔 노드 0 · 노드가 없는 글자 2096 · 파일에 적힌 글자 2136
```

**이 파일은 있는 행만 고친다.** 「노드가 없는 글자」가 0 이 아니면 씨앗 적재가 먼저다.

**이 칸이 비어 있으면 부품을 고칠 때마다 2,136자를 전부 찍어야 한다.** 무엇이 올라가 있는지 모르면 무엇이 달라졌는지도 모르기 때문이다. `pnpm seed:parts-sql --all` 은 그래서 안전하지만 파일이 길다.

적용한 사람이 여기 커밋을 적는다. 그 뒤부터는 `pnpm seed:parts-sql --since <그 커밋>` 으로 바뀐 것만 찍는다.

```bash
pnpm seed:parts-sql --all --out db/manual/parts-sync-<날짜>.sql   # 접속하지 않는다. SQL 만 찍는다
# 받은 사람이 파일을 읽고 돌린다. 1번 질의가 실제로 바뀔 줄 수를 먼저 알려 준다.
```

찍어낸 UPDATE 는 `meta->'parts'` 가 **실제로 다른 줄만** 건드린다. 두 번 돌리면 두 번째는 0 줄이다.

`manual/` 은 마이그레이션이 아니다. `pnpm db:migrate` 가 안 본다. 한 번 손으로 돌리고 나면 위 표에 커밋을 적고 파일은 기록으로 남긴다.

## 두 개의 연결

| 변수 | 역할 | 쓰는 곳 |
| --- | --- | --- |
| `DATABASE_URL_ADMIN` (없으면 `DATABASE_URL`) | 테이블 소유자 (Neon 기본 역할). Vercel Neon 통합은 이걸 `DATABASE_URL` 로 주입한다 | 마이그레이션, 공용 참조 데이터 적재, 백업 |
| `ANCHOR_DATABASE_URL` | `anchor_app` (BYPASSRLS 없음, 0001 이 SQL로 생성) | 앱 런타임 전부 |

Neon 콘솔·API로 만든 역할은 `neon_superuser` 멤버라 RLS를 우회한다. 앱 역할을 콘솔에서 만들면 RLS가 무력화된다. 반드시 마이그레이션이 만든 `anchor_app` 을 쓴다.

## DB 를 쓰는 테스트

```bash
pnpm test:db     # DATABASE_URL_ADMIN 과 ANCHOR_DATABASE_URL 둘 다 필요하다
```

**수보다 먼저 출처 한 줄이 나온다.**

```
DB: anchor_local@127.0.0.1:5432 (anchor_owner)
마이그레이션: 0001–0008 적용 (8/8) · 레포와 8/8 일치
※ 아래 초록·빨강은 이 상태 위의 값이다.
```

**조건 없는 초록이 거짓말을 하기 때문이다.** 같은 명령이 한 컨테이너에서는 전부 초록이고 다른 컨테이너에서는 셋이 빨강이던 날이 있었다 — 뒤쪽에 `0008` 이 없어서였고, 그건 그 셋이 제 일을 한 것이다. 그런데 앞쪽 초록만 인용되면 **막힌 마이그레이션이 풀렸다는 뜻으로 읽힌다.** 숫자에는 어느 값 위에서 난 것인지를 붙인다.

**어긋나면 같은 줄이 그것도 말한다** — 맞을 때만 말하는 줄은 맞다는 것을 증명하지 못한다:

```
마이그레이션: 0001–0007 적용 (7/8)
  안 올라간 것: 0008_recordings_client_id.sql
  어긋난 것: 0007_measure_columns.sql (원장 100f2d2c5a4d… / 레포 dc498df7fb86…)
```

**어긋나도 멈추지 않는다.** 여기서 막으면 어긋난 쪽은 무엇이 지나가고 무엇이 떨어지는지조차 못 본다. 이 줄의 일은 막는 것이 아니라 말하는 것이다. 읽기만 하고 아무것도 안 고친다.

`scripts/test/*.test.ts` 는 `node:test` 로 돈다(의존성 없음). **앱 역할로 붙어 진짜 코드 경로를 타므로 RLS 까지 같이 시험한다** — 질의를 테스트에 베껴 쓰면 코드가 아니라 사본을 시험하게 된다.

쓰는 계정은 `fixture-` 로 시작하는 것뿐이고 끝나면 지운다. **프로덕션 연결로 돌리지 않는다.** 로컬이나 일회용 DB 를 쓴다.

### 갑자기 마흔일곱이 빨개졌을 때 — 「그거겠지」 대신 한 줄

로컬 Postgres 가 하루에 **열두 번** 죽었다. 한 번 죽을 때마다 DB 를 쓰는 테스트가 전부
`connect ECONNREFUSED 127.0.0.1:5432` 로 빨개진다. **낫지 않는 거짓 경보가 열두 번 울리면
열세 번째를 안 보게 된다** — 실제로 한 번은 "또 그거겠지" 하고 초록을 확인하기 전에 푸시했다.
사람 탓이 아니라 신호 탓이라, 짐작 대신 **가르는 한 줄**을 둔다:

```bash
uptime      # 기계가 방금 켜졌나
```

**기계(컨테이너)의 `up` 이 몇 분이면 Postgres 가 죽은 게 아니라 컨테이너가 회수된 것이다.**
`pg_ctlcluster 16 main start` 로 살리고 다시 돌리면 그대로 초록이다. 실제로 열두 번째 때
`up 9 min` 이었고, Postgres 로그의 마지막 줄은 **정상 체크포인트**였다(죽은 흔적이 아니다).

**기계가 몇 시간째 떠 있는데 Postgres 만 죽었으면 그건 진짜다.** 그때는 로그를 읽는다.

### 그리고 판정을 파이프에 흘리지 않는다

```bash
pnpm test:db | grep "# pass" && git push     # ← 틀렸다
```

**`grep` 이 성공하면 `&&` 가 이어진다.** 빨간 줄 여덟이 떠 있어도 `# pass` 라는 **글자**를 찾은
것만으로 푸시가 나간다 — 실제로 그렇게 한 번 나갔다. 파이프는 **시험의 종료 코드를 버린다.**

**수를 눈으로 보는 것과 초록을 확인하는 것은 다른 일이다.** 수는 사람이 읽고, **통과 여부는
종료 코드가 말한다.**

### 밀기 전 차례 넷

```bash
git fetch origin main && git merge origin/main                           # ① 먼저 합친다
pnpm typecheck && pnpm lint && pnpm build && pnpm test:db > /tmp/t.log   # ② 합친 것을 잰다. 종료 코드로 잇는다
git merge-base --is-ancestor origin/main HEAD                            # ③ 조상인지 묻는다
git push -u origin <branch>                                              # ④
grep -E "^# (pass|fail)" /tmp/t.log                                      # 수는 사람이 읽는다
```

**①과 ②의 순서가 전에는 거꾸로였다.** 검증을 먼저 하고 합쳐서 밀면 **미는 것은 합친 결과인데 잰
것은 내 나무**가 된다 — 남의 커밋이 얹힌 채로 한 번도 안 재고 나가는 것이다. 실제로 그 차례대로
하다가, `main` 이 움직인 날 **합친 트리를 확인 안 한 채 프로덕션에 밀 뻔했다.** 합치기 전에도 재도
된다(내 것이 성한지 먼저 아는 값이 있다). **다만 미는 것을 묶는 판정은 ②다.**

**②와 ③이 하루에 한 번씩 샜다.** ②는 파이프가 판정을 버려서, ③은 **`fetch` 를 관계 확인으로 여겨서**다
— `fetch` 는 저쪽의 최신을 주지 **이쪽과의 관계**를 안 준다. 「최신을 받았다」와 「내가 그 위에 서
있다」는 다른 물음이고, 앞엣것으로 뒤엣것을 대신한 날 가지가 17커밋 뒤처진 채 fast-forward 라고 적혔다.

**셋 다 「했다고 여겼는데 안 물은」 자리**라 조심해서는 안 막힌다. 그래서 차례를 하나로 묶어 둔다.
여럿이 미는 동안엔 합친 순간부터 다시 늙으므로, ①은 밀 때 그 자리에서 한다 — 미리 합쳐 둔 것은
**「충돌을 미리 봄」**이지 밀 수 있게 된 것이 아니다.

붙들어 두는 것 넷. **내보내기 목록이 스키마에서 새지 않는가**, **계정 삭제가 모든 표에 닿는가** (아래), 그리고 **재전송 멱등 키**(0008)가 스키마에 서 있는가 — 이게 빠지면 다시 보낸 녹음이 새 회차로 앉아 5회차 자리에 4회차 소리가 앉는다. 그리고 **`encounters` 가 덧붙이는가**. 뒤쪽은 한 번 덮어쓰기로 돌아간 적이 있고, 그때 코드에는 반대로 적힌 주석이 또렷하게 달려 있었다. **틀려도 화면은 똑같이 돌고 인식률만 위로 부푼 채 D+14 까지 간다** — 그런 문장은 주석이 아니라 테스트로 적는다.

### 내보내기와 삭제 — 같은 질문의 양쪽

둘 다 "전부" 를 약속하는데 틀려도 티가 안 난다. 조용히 틀렸을 때 남는 말이 정반대다.

| | 조용히 틀리면 |
| --- | --- |
| 내보내기 | 사용자가 **다 가졌다고 믿는데** 안 가졌다 |
| 삭제 | 사용자가 **다 지웠다고 믿는데** 안 지워졌다 |

내보내기는 손으로 적은 표 목록을 돈다(`src/lib/db/export-tables.ts`). 삭제는 목록이 없다 — `users` 행 하나를 지우고 FK 가 CASCADE 로 흘리게 둔다. 목록이 없으니 목록 표류도 없어서 **삭제 쪽 설계가 낫다.** 대신 가정이 하나 생긴다: 사용자 행을 가진 표가 전부 `users` 까지 이어져 있다는 것.

두 규칙을 `pnpm test:db` 가 스키마에서 읽어 견준다. **차이가 있으면 선언된 차이여야 한다.**

- `src/lib/db/export-tables.ts` — 내보내는 표와 그 예외
- `src/lib/db/delete-paths.ts` — 삭제가 안 닿아도 되는 표와 그 이유

**FK 가 있다는 것과 지워진다는 것은 다르다.** 삭제 쪽 검사는 FK 의 존재가 아니라 **규칙**을 본다. `users` 로 가는 FK 의 규칙이 `SET NULL` 이면 행은 살아남는데, `nodes` · `edges` 는 `user_id` 가 NULL 을 허용하고 이 스키마에서 **NULL 은 "공용 참조 데이터"** 를 뜻한다(`0001_init.sql:92`). 지운 계정의 개인 노드가 주인만 잃고 남아 모든 계정이 읽게 된다 — 남는 것보다 나쁜 새는 것이고, "FK 가 있나" 만 보는 검사는 이걸 통과시킨다. 규칙만 `SET NULL` 로 바꿔 로컬에서 확인했다.

그리고 **권한 쪽은 내보내기보다 삭제가 나쁘다.** 내보내기는 `SELECT` 를 잃으면 질의가 터져 티가 난다. 삭제는 RLS 정책이 `DELETE` 를 안 덮으면 **`DELETE 0` 에 오류가 없다.** 라우트는 그대로 `{ ok: true }` 를 돌려주고 뒤이어 로그인까지 지워져 **다시 들어와 지울 길도 없다.** 그래서 스키마 검사와 별개로 라우트가 **지워진 행 수를 본다.**

## 회차는 왜 저장된 값인가 — 그리고 고칠 때 무엇이 답이 아닌가

`recordings.attempt` 는 서버가 INSERT 직전 `count(*)+1` 로 세어 **저장하는 파생값**이다. 제약이 없어서 같은 대상에 두 요청이 동시에 들어오면 **둘 다 같은 수를 받을 수 있다.** 그러면 `pnpm measure` 의 1회차·5회차가 둘 중 아무거나 집고, 표에는 멀쩡한 거리가 뜨는데 어느 회차를 잰 값인지는 모른다.

**아직 한 번도 안 일어났다.** 사용자가 한 명이고, 같은 덩어리에 동시 녹음이 나려면 두 탭이나 이중 제출이 있어야 한다. 그래서 지금은 고치지 않고 `pnpm measure` 가 그 대상 수를 머리말에 낸다. 그 대상을 표에서 빼지는 않는다 — 거리가 멀쩡해 보이는 것이 이 사고의 모양이라, 숨기면 더 나빠진다.

### `UNIQUE (대상, 회차)` 는 답이 아니다

걸면 동시 요청 둘 중 **둘째 쓰기가 실패한다.** 그 둘째는 사용자가 실제로 낸 녹음이다. **지금은 "거리를 못 믿는 행 하나" 인데, 유니크를 걸면 "사라진 녹음 하나" 가 된다** — `CLAUDE.md` 의 "추측 한 번, 녹음 한 번도 유실 없음" 을 깨는 쪽으로 바뀐다. 재시도를 붙이면 되긴 하지만, 그러면 유니크는 **재시도를 트리거하는 장치**지 답이 아니다.

### 답은 `attempt` 를 저장하지 않는 것

사실은 언제 말했는가이고 회차는 거기서 나오는 **판정**이다. 읽을 때 `row_number() OVER (PARTITION BY 대상 ORDER BY 말한 시각)` 로 매기면 세는 카운터가 없으니 **경합 자체가 없다.** `pnpm measure` 의 재만남 쪽이 이미 그 모양이다.

**다만 한 칸이 먼저 필요하다 — outbox 때문이다.** 저장 시각으로 매기면 **재전송이 역사를 다시 매긴다.** 오프라인에서 T1 에 말한 녹음이 T3 에 저장되면 저장 순서로는 그게 마지막 회차가 되는데, **말한 순서와 저장된 순서가 다른 것이 outbox 의 존재 이유다.** `0008` 은 `client_id` 만 달고 말한 시각이 없다.

> 파생으로 바꾸는 날, `client_id` 를 찍는 **그 자리에서** 「말한 시각」도 같이 찍는다. 순서는 저장 시각이 아니라 말한 시각으로 매긴다.

`client_id` 를 브라우저가 녹음을 만든 자리에서 붙이기로 한 것과 같은 이유다 — 서버가 만들면 재전송마다 달라지듯, 서버 시각으로 매기면 재전송마다 회차가 달라진다.

**급할 때 유니크로 손이 가지 않게 여기 적어 둔다.** 지금까지 쌓인 행은 `attempt` 가 저장돼 있어 그대로 읽히므로, 바꾸는 날 옛 행을 못 쓰게 되지는 않는다.

## RLS 동작 방식

```
withUser(userId, tx => ...)
  BEGIN
  SELECT set_config('app.user_id', $userId, true)   -- 트랜잭션 로컬
  ...쿼리...                                          -- 정책: user_id = app.current_user_id()
  COMMIT
```

- 설정이 없으면 `app.current_user_id()` 가 NULL → 모든 정책이 false → 아무 행도 안 보인다.
- 모든 사용자 테이블은 `FORCE ROW LEVEL SECURITY` 라 소유자 연결에서도 정책이 적용된다. admin 연결로 사용자 데이터를 보려면 `SET app.user_id` 를 해야 한다. 이건 의도된 마찰이다.
- `nodes`, `edges` 는 `user_id IS NULL` 행이 공용 참조 데이터(KANJIDIC2, IDS, 한자음, 어원)다. 읽기는 모두, 쓰기는 admin 스크립트만.

| --- | --- | --- |
