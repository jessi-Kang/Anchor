# 세션 운영 규칙 (누가 무엇을 소유하는가)

Anchor 는 사람 1명(Jessi)과 여러 Claude 세션이 동시에 만든다. 세션은 서로의 작업 트리를 볼 수 없고 브랜치로만 만난다.
그래서 **소유권·통합 순서·완결 기준**을 여기에 적는다. 화면 순서는 `docs/FLOW.md`, 왜는 `docs/SPEC.md`, 이 파일은 "누가 어디를 고치는가".

## 1. 멤버와 소유 영역

세션끼리 메시지를 보낼 때는 이름이 아니라 세션 ID 가 주소다: `create_trigger(persistent_session_id=<ID>, 스케줄 없음)` + `fire_trigger`.

### 묶음

일하는 세션은 모두 `anchor` 태그를 달고, 그 아래 네 묶음으로 나뉜다. 묶음은 소유 구조와 같다 — 기준을 쓰는 쪽, 만드는 쪽, 보는 쪽, 조율.

| 묶음 | 태그 | 누가 | 무엇을 소유하는가 |
| --- | --- | --- | --- |
| 조율 | `anchor-lead` | PM | 결정과 전달. 산출물을 직접 만들지 않는다 |
| 기준 | `anchor-spec` | 기획 · 문서 | 문서. 무엇을 만들지와 지금 무엇이 참인지를 쓴다 |
| 제작 | `anchor-build` | 디자인 · 개발 | 화면과 코드. 기준 문서를 그대로 옮긴다 |
| 검증 | `anchor-verify` | QA · 보안 | 읽기 전용. 만든 것이 기준과 맞는지 본다 |

끝난 세션은 `anchor` 를 떼고 `anchor-closed` 를 단다. 명단에 섞이지 않게 하려는 것이고, 기록은 남는다.

묶음이 넷인 이유는 **같은 묶음 안에서는 파일이 겹치지 않고, 다른 묶음끼리는 반드시 PM 을 거치기 때문**이다. 제작이 기준을 고치거나 검증이 코드를 고치면 그 자리에서 충돌한다.

**세션은 승인 없이 도구를 쓸 수 있는 모드로 띄운다.** plan 모드 세션은 도구를 쓸 때마다 사람의 승인을 기다리므로 Jessi 의 손을 붙잡는다. 권한 모드는 만든 뒤에 바꿀 수 없으니, 잘못 떴으면 같은 역할을 새 세션으로 세우고 옛 세션은 멈춘다. 브랜치에 main 에 없는 커밋이 없는지 먼저 확인한다.

보내는 길:
- QA 가 찾은 것 → 코드 결함은 **개발**, 기획 문제는 **PM**. QA 가 두 곳에 같은 건을 보내지 않는다.
- 보안이 찾은 것 → 전부 **PM**. 등급이 "샘"(남의 데이터가 보이거나 비밀값이 나간다)이면 다른 모든 일보다 먼저 고친다.
- 디자인이 화면 순서·화면 추가/삭제·문구 의도를 바꾸고 싶으면 → **PM**. PM 이 결정하고 **기획**이 `docs/FLOW.md` 에 반영한 뒤 **개발**에 알린다.
- 개발이 기획 문서와 다르게 만들어야 할 이유를 찾으면 → **PM**. 혼자 판단해서 문서와 다르게 만들지 않는다.
- 문서에서 문체·중복·사실 불일치를 발견하면 → **문서**. 기준 문서(SPEC·FLOW·SITEMAP)에 대한 것이면 문서 세션이 고치지 않고 **PM** 에게 목록으로 보낸다.
- 남의 영역이 고쳐져야 하면 직접 고치지 말고 그 세션에 요청한다. 두 세션이 같은 파일을 고치면 둘 중 하나는 반드시 버려진다.

## 2. 브랜치와 통합

- `main` 이 프로덕션. 세션마다 자기 작업 브랜치.
- **작업 단계가 끝나면 그 자리에서 푸시한다.** 세션 컨테이너는 사라지고, 푸시하지 않은 커밋은 같이 사라진다.
- 푸시 전에 `git merge origin/main` → `pnpm typecheck && pnpm lint && pnpm build` → 통과하면 `main` 에도 푸시.
- fast-forward 가 안 되면 `main` 을 자기 브랜치로 merge 한 뒤 푸시한다. 남의 커밋을 되돌리거나 force-push 하지 않는다.
- 기준 문서(`docs/FLOW.md`)가 바뀌면 기획 세션이 Dev·디자이너에게 알린다. 코드가 문서와 다르면 코드가 틀린 것이다.

## 3. 완결 기준 (이게 되면 1차 완결)

`docs/FLOW.md` 1장의 첫 방문 경로가 실제로 끝까지 돈다.

1. 로그인 → 언어 → 예시 자료 → 뽑기 → 가나 1회 → 카드(F04 + 장면 5) → 말하기 → 그래프 → 홈
2. 404 0건, 어느 화면에서도 홈까지 2탭, 5분 안
3. `pnpm typecheck && pnpm lint && pnpm build` 통과, Vercel 프로덕션 배포 성공
4. Anchor · QA 가 `docs/QA.md` 의 검증 플로우를 초기화된 계정으로 처음부터 끝까지 돌려 "막힘" 등급 결함 0건

판정 절차는 셋이다.

1. **QA 가 검증 플로우를 만든다.** 무엇을 어떤 순서로 눌러 보는지, 각 지점에서 무엇이 참이어야 하는지, 등급(막힘 / 헷갈림 / 다듬기)을 어떻게 나누는지를 `docs/QA.md` 에 적는다. 플로우는 다음 사람이 그대로 따라 할 수 있어야 한다.
2. **QA 가 돌리고 판정한다.** 항목마다 통과·실패와 등급, 실패면 무엇이 일어났는지와 `docs/FLOW.md` 의 어느 절과 어긋나는지.
3. **PM 과 기획이 그 결과를 보고 판단한다.** 코드가 틀렸는지, 기준 문서가 틀렸는지, 완결로 볼 수 있는지. QA 는 사실을 대고 등급을 매기고, 완결 여부를 스스로 선언하지 않는다. 기획과 PM 의 판단이 갈리면 PM 이 정한다.

그다음이 영어 대화 루프(F13~F14) → 재만남(F12) → 하루 끝(F15).

## 5. 문서 규칙

문서는 무슨 일이 있었는지의 기록이 아니라 지금 무엇이 참인지의 서술이다.

- **대화·결정 과정을 그대로 옮기지 않는다.** "논의 끝에 이렇게 하기로 했다", "원래는 A였는데 B로 바꿨다" 같은 서사는 쓰지 않는다. 결론만 현재형 규칙으로 쓴다. 변경 이력은 git 커밋과 vibelog 가 담당한다.
- 새 결정이 들어오면 덧붙이지 말고 **어긋나는 옛 문장을 지운다.** 같은 사실이 두 문서에 다르게 적혀 있으면 한쪽을 지우고 다른 쪽을 가리킨다.
- 문체: 한국어. 한 문장에 한 사실. 단정적인 평서문. 수식어를 걷어낸다. 목록보다 표가 맞으면 표. 제목은 명사구.
- 분량을 늘리는 것은 성과가 아니다. 같은 내용을 더 짧게 만들면 그게 성과다.

문서마다 맡은 것이 다르다. 겹치면 둘이 어긋난다.

| 문서 | 무엇을 담는가 |
| --- | --- |
| `docs/SPEC.md` | 왜 이렇게 만드는가 (원칙·모델·로드맵) |
| `docs/FLOW.md` | 사용자가 밟는 화면 순서와 각 화면의 목적 |
| `docs/SITEMAP.md` | 라우트와 화면 파일의 대응 |
| `docs/STATUS.md` | 지금 실제로 있는 것과 없는 것. 상태만 적고 계획은 적지 않는다 |
| `docs/TEAM.md` | 누가 어디를 고치는가, 통합 규칙, 완결 기준, 우선순위 |
| `docs/BACKUP.md` | 백업 세 층과 복구 절차 |
| `README.md` | 처음 보는 사람에게 프로젝트를 설명하는 한 장 |

### 기준 문서 편집 패스

`docs/SPEC.md` · `docs/FLOW.md` · `docs/SITEMAP.md` 는 기획 소유다. 문서 세션은 평소에 이 셋을 고치지 않는다.
한 단계(P0·P1 등)가 끝날 때마다 PM 이 문서 세션에 **편집 패스**를 연다. 그 동안만 문서 세션이 세 파일을 고치고, 기획은 쓰지 않는다. 문서 세션이 푸시하고 PM 에게 알리면 패스가 닫힌다.

## 6. 결정과 보고

Jessi 는 세션 운영을 PM 에게 일임했다. 세션은 다음 두 가지를 스스로 하지 않는다.

- **일이 없을 때 새 일을 만들지 않는다.** 맡은 단계가 끝나면 PM 에게 알리고 기다린다. 다음 일은 PM 이 준다. 우선순위(4장)를 넘겨짚어 다음 단계를 먼저 시작하지 않는다.
- **판단이 필요한 것을 혼자 정하지 않는다.** 화면을 더할지 뺄지, 기준 문서와 다르게 만들지, 두 원칙이 부딪힐 때 무엇을 택할지는 PM 이 정한다. 의견을 붙여 PM 에게 보낸다. 이미 기준 문서에 원칙으로 적혀 있는 것(문구·어휘·색·버튼 규칙 등)은 그냥 따르고 묻지 않는다.

그래서 세션은 **단계가 끝나면 결과를, 막히면 막힌 것을 그때그때 PM 에게 보낸다.** 보고가 없는 세션은 아침 보고에 "진행 없음"으로 올라간다.

PM 은 매일 아침 8시(KST) Jessi 에게 한 번 보고한다. 담는 것은 넷이다.

| 무엇 | 내용 |
| --- | --- |
| 어제 끝난 것 | main 에 들어간 것만. 브랜치에만 있는 것은 "진행 중"이다 |
| 지금 막힌 것 | 무엇이 왜 막혔는지, PM 이 무엇을 했는지 |
| Jessi 가 결정할 것 | PM 이 정할 수 없는 것만. 없으면 "없음" |
| 오늘 할 것 | 세션별 한 줄 |

Jessi 가 결정할 것은 돈이 들거나(유료 플랜·외부 계정), 제품의 방향을 바꾸거나, 사람이 직접 해야 하는 일(복구 리허설 등)뿐이다. 그 밖의 것은 PM 이 정하고 결과만 보고한다.

| 마이그레이션 순서 | 마이그레이션은 **프로덕션에 적용하기 전에 `main` 에 들어간다.** 프로덕션 스키마가 `main` 보다 앞서면, `main` 을 체크아웃해 복구했을 때 없는 표가 생기고 백업 안의 행이 들어갈 곳을 잃는다 |
| DB 작업 경로 | 세션에서 DB 에 닿는 길은 **Neon MCP** 다. 조회도 마이그레이션 적용도 그 길로 한다. 스크립트가 막힌 이유는 포트가 아니다 — `scripts/lib/admin-client.ts` 는 호스트가 `*.neon.tech` 면 Neon 서버리스 드라이버(HTTPS 443)를 쓰므로 `pnpm db:migrate` 는 5432 와 무관하게 돈다. 막는 것은 하나, 세션에 연결 문자열이 없다는 것이다. `get_connection_string` 은 하네스가 막는다(Credential Materialization). `psql` 은 5432 를 쓰므로 이 환경에서 Neon 에 닿지 못한다 |
| 스키마 변경 | `db/migrations/` 의 SQL 파일로만 한다. 파일이 원본이고, 적용은 Neon MCP 로 그 파일의 SQL 을 실행하는 것이다. MCP 로 프로덕션 DB 에 직접 DDL 을 치지 않는다. 복구(`docs/BACKUP.md` 절차 C)가 `pnpm db:migrate` 로 스키마를 다시 만드는 전제 위에 서 있어, 파일에 없는 테이블은 복구하면 행째로 사라진다. 조회(SELECT)는 MCP 로 해도 된다 |
| 만드는 순서 | `docs/TEAM.md` 4장이 정한다. `docs/SPEC.md` 9장은 무엇을 검증하는가를 정하고 순서를 정하지 않는다 |

## 8. 모델과 비용

세션마다 쓰는 모델이 다르다. 판단이 무거운 자리에 비싼 모델을, 반복이 많은 자리에 싼 모델을 둔다. 토큰 비용은 PM 이 본다.

| 역할 | 모델 | 왜 |
| --- | --- | --- |
| PM | 가장 센 것 | 결정이 틀리면 모두가 되돌아간다. 대신 PM 은 전달·기록을 직접 하지 않는다 |
| 기획 · 보안 · 디자인 | 센 것 | 원칙이 부딪히는 자리를 가른다. 대신 작업량이 적다 |
| 개발 | 중간 | 코드 양이 많아 단가가 곧 비용이다 |
| QA · 문서 | 중간 | 정해진 목록을 돌리고 문장을 다듬는다. 판단은 PM 과 기획이 한다 |
| 기록 | 가장 싼 것 | 받은 것을 줄여 적는다. 판단하지 않는다 |
| UX writer | 센 것 | 「이 말이 통하는가」는 판단이고, 이 서비스는 문구가 곧 제품이다 |
| 테스터 | 중간 | 역할 연기하고 헷갈린 것을 그대로 올린다. 판단은 UX writer 와 PM 이 한다. 아홉이라 단가가 아홉 배로 붙는다 |

**모델 고르기는 세션을 세우는 한 단계다.** 기본값으로 세우지 않는다. Jessi 가 정한 규칙이다 — 새 세션을 열 때마다 **그 역할에 최적의 비용을 쓰는 모델**을 고른다. 위 표는 이미 있는 자리를 적은 것이지 고르는 법이 아니고, 새 역할은 표에 없다.

고르는 법은 두 가지를 본다.

**하나, 이 자리가 판단하는 자리인가 옮기는 자리인가.** 원칙이 부딪히는 것을 가르고, 문구가 통하는지 보고, 무엇을 먼저 할지 정하는 자리는 센 것이다. 정해진 목록을 돌리고, 받은 것을 옮겨 적고, 시킨 대로 역할을 연기하는 자리는 싼 것이다. 물음으로 바꾸면 이렇다 — **이 자리가 틀리면 누가 되돌아가는가.** 자기 혼자면 싼 것으로 족하고, 여럿이 되돌아가면 센 것이 싸다.

**둘, 몇 개를 세우는가.** 같은 역할을 아홉 세우면 단가 차이도 아홉 배다. 하나짜리 자리에서는 한 단계 센 것을 골라도 되고, 여럿짜리 자리에서는 한 단계 싼 것이 맞다.

**고른 이유를 세션을 세울 때 한 줄로 남긴다.** 안 남기면 다음 사람이 그 자리를 다시 세울 때 또 처음부터 고민하거나, 아무 생각 없이 같은 것을 복사한다.

**세션의 모델은 만든 뒤에 바꿀 수 없다.** 바꾸려면 같은 역할로 새 세션을 세우고 옛 세션을 보관한다(Jessi 가 앱에서 직접 바꾸는 길도 있다). 그래서 모델은 세션을 세울 때 정하고, 이미 도는 세션은 컨텍스트가 차서 교체할 때 함께 바꾼다.

**비용을 줄이는 것은 모델 교체보다 컨텍스트 관리다.** 오늘 가장 비싼 세션은 가장 센 모델을 쓴 세션이 아니라, 승인 대기로 같은 맥락을 1,500번 다시 읽은 세션이었다. 그래서: 한 세션이 여러 단계를 물고 있지 않게 자르고, 끝난 세션은 보관하고, 사람 승인을 기다리는 구조를 만들지 않는다.

**진행 보고는 기록으로, 판단이 필요한 것만 PM 으로.** 같은 것을 둘에게 보내지 않는다.

## 9. 거부에는 두 종류가 있다

세션이 도구를 부르다 막혔을 때, 무엇에 막혔는지를 먼저 가른다. 둘을 섞으면 안전장치를 장애물로 취급하는 습관이 든다.

| 무엇에 막혔나 | 어떻게 하나 |
| --- | --- |
| **허용 목록에 그 도구가 없어서** 승인창이 뜨고 거부됐다 | 같은 일을 하는 다른 경로로 간다. 경로가 없으면 PM 에게 알린다 |
| **가드레일이 막았다** — 자격증명을 명령에 싣기, 환경에서 비밀값 훑기, 프로덕션 데이터를 지우거나 되돌리기 | **멈추고 PM 에게 보고한다.** 우회로를 찾지 않는다 |

둘째 줄에서 우회로를 찾기 시작하면, 데이터 원칙을 지키자고 만든 팀이 그 원칙을 깨는 모양이 된다. 막힌 것이 어느 쪽인지 분명하지 않으면 둘째로 본다.

## 10. 흩어진 것을 찾을 때 — 찾는 말이 곧 찾을 수 있는 범위다

하루에 같은 모양의 결함이 여섯 번 났다. 조사가 네 곳, 자료를 부르는 이름이 일곱 곳. 전부 **한 가지 결정이 여러 곳에 흩어져 있던 것**이다. 그걸 찾는 과정에서 같은 함정에 세 번 빠졌다 — **"두 곳인 줄 알았는데 여섯 곳"**.

그래서 규칙 셋.

**하나. 한 자리를 고치라는 지시를 받으면, 같은 종류의 자리를 전부 훑고 나서 고친다.** 지시에 적힌 자리만 고치면 다음 라운드에 나머지가 올라온다. 훑은 범위와 나온 개수를 보고에 적는다.

**둘. 못 찾았을 때는 "없다"가 아니라 "이 말로 찾아서 없었다"로 보고한다.** 디자인이 참고 화면에서 자료 이름을 훑을 때 `日経 기사` 로 찾아 **`日経` 한 글자짜리를 놓쳤다.** 그래서 "규칙대로 있던 유일한 화면"이라던 F12 가 사실은 같은 화면 안에서 자료를 두 이름으로 부르고 있었다. 찾는 말이 좁으면 결과도 좁다. 후보를 넓혀 다시 훑고, 무엇으로 찾았는지를 남긴다.

**셋. 참고 화면으로 잡히는 것과 코드로만 잡히는 것을 가른다.** `inputName()` 이 언어를 안 봐서 영어 예시도 "아침 기사"로 불린 것은 **참고 화면으로는 영영 안 잡힌다** — 참고에 영어 자료가 한 행뿐이라 드러날 자리가 없었다. 문구가 어긋나는 것은 참고 화면으로, **같은 코드가 여러 경우에 다르게 굴어야 하는 것은 코드로** 본다.

### 모으는 것이 항상 옳지는 않다

흩어진 것을 한 곳으로 모으는 게 이 장의 요지이지만, 반대 방향으로도 틀릴 수 있다. 자료 이름을 한 곳으로 모으면서 규칙을 "예시 자료는 '아침 기사' 하나"로 적었더니 **세 언어가 한 이름에 뭉개졌다** — 영어 예시(회의 노트)도 "아침 기사"로 불렸다.

**모으기 전에 무엇이 같고 무엇이 다른지를 먼저 가른다.** 같은 것을 여러 곳에 두는 것과, 다른 것을 한 곳에 뭉개는 것은 같은 크기의 잘못이다.

### 찾기 전에 — 흩어뜨리지 않는 쪽이 싸다

여기까지는 이미 흩어진 것을 찾는 법이다. 오늘 여섯 번 다 **흩어진 뒤에** 찾았다. 뿌리는 하나였다 — **새 것을 더할 때 옛 문장을 안 지운다.**

추측 화면(F17)을 넣으면서 FLOW 의 F13 행은 여전히 F14 로 가고 있었고, "F14 만 두 탭", "두 화면은 1′장 표에", CLAUDE.md 의 "F13~F14" 가 다 옛말로 남았다. F14 셀에는 영어 문장이 **두 번** 적혔다 — 옛 줄을 안 지우고 새 줄을 덧붙여서다.

5장이 이미 "덧붙이지 말고 어긋나는 옛 문장을 지운다"고 적어 두었는데도 났다. 규칙이 있어도 **그 자리를 찾는 동작**이 없으면 안 지켜진다. 그래서 동작으로 적는다.

**화면·규칙·이름을 새로 더하기 전에, 그 이름이 나오는 자리를 먼저 전부 찾는다.** 새 화면이면 그 앞뒤 화면 ID 로, 새 규칙이면 그 규칙이 다루는 말로. 문서만이 아니라 `CLAUDE.md`·`design/`·코드까지. 찾은 자리 목록을 만들고 시작하면 "덧붙이기"가 구조적으로 안 된다 — 고칠 자리가 이미 눈앞에 있기 때문이다.

같은 값이 두 문서에 적혀 있으면 그 자체가 다음 사고다. 한쪽만 고쳐진다.

## 11. 결론이 맞아도 이유가 틀리면 고친다

기획이 FLOW 에 재만남 틴트의 기준을 적으면서 이유를 이렇게 썼다: "`knows_meaning` 하나로는 **틀린 추측으로 끝낸 카드**가 새 것으로 다시 진해진다."

**사실이 아니었다.** `kanji.ts` 의 `lightUp` 은 맞았는지를 **확신값에만** 쓰고(0.9 / 0.6), `SET knows_meaning = true` 는 조건 없이 돈다. 맞았든 틀렸든 켜진다.

고른 집합은 맞았고 구현도 맞았다. **틀린 것은 왜냐는 부분 하나뿐이었다.** 그래서 더 위험하다 — 결론이 맞으니 아무도 그 문장을 의심하지 않는다. 카드 큐에서 틀린 한자를 다시 낼지 정할 때 누군가 그 문장을 근거로 삼았으면 잘못된 큐가 나왔을 것이다.

기획이 자기 실수의 모양을 이렇게 적었다: **코드를 읽고 쓴 결론에, 읽지 않은 이유를 붙였다.**

**그래서: 문서에 코드의 동작을 이유로 쓸 때는 그 줄을 열고 쓴다.** "아마 이래서일 것이다"를 단정형으로 적지 않는다. 확인 못 했으면 이유를 비워 두는 편이 낫다 — 빈 자리는 다음 사람이 채우지만, 틀린 이유는 다음 사람이 딛고 선다.

### 지시에 적은 기준도 같다

이 건을 고치다가 하나가 더 나왔다. PM 이 QA 에 준 시험 기준("이 자료에서 이미 만났는가")도 코드보다 좁았다 — `anchors` 는 자료를 가리지 않는다. **QA 는 그 문장을 그대로 시험 기준으로 삼고 있었으므로, 안 잡았으면 통과인 것을 결함으로 올렸을 것이다.**

지시에 적는 기준은 문서에 적는 규칙과 같은 무게다. 코드의 동작을 기준으로 줄 때는 그 줄을 보고 주고, 틀린 걸 알면 **상대가 보고하기 전에** 정정을 보낸다.

### 코드 주석에만 있는 규칙은 규칙이 아니다

같은 날 반대 짝이 나왔다. 앵커 단어를 아직 안 푼 한자에 붙이지 않는다는 규칙이 `src/app/graph/page.tsx` 주석에만 있었다 — 이유까지 또렷하게, 판정하는 자리와 아닌 자리를 갈라서. 그런데 **어느 문서에도 없어서 같은 질문이 세 번 돌았다.** 디자인은 "F12 전용인가"를 물었고, 나는 참고 화면을 고치라고 넘겼고, 기획은 새로 정하려 했다. 셋 다 이미 있는 답을 못 찾았다.

앞 절이 "문서에 코드와 다른 이유를 적지 마라"라면 이쪽은 **"코드에만 적고 끝내지 마라"**다. 주석은 그 파일을 여는 사람만 읽는다. 화면·문구·원칙에 걸리는 판단을 코드에서 내렸으면, 그 판단은 문서에 올라가야 한다. 주석에는 문서를 가리키는 한 줄만 남긴다 — 온전한 문장이 두 곳에 있으면 한쪽만 고쳐진다.

**어디에 적을지 헷갈리면 이렇게 가른다.** 다른 자리에서도 같은 선택을 하게 될 판단이면 문서다. 이 파일 안에서만 뜻이 있는 것(왜 이 함수로 묶었는지, 어떤 값이 왜 nullable 인지)이면 주석이다.
